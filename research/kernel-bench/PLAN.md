# 表格内核对比测试方案

目的：在 IronCalc 和 GridCraft 内核之间选一个，作为我们表格的内核。界面不在这次比较里。

状态：2026-10-20 开工（作者决定和黑客松同时做，由 agent 自动开发）。数字门槛都是「建议」，作者没确认。

## 1. 候选

| | IronCalc | GridCraft 内核 |
|---|---|---|
| 版本 | 0.9.0（crates.io，2026-10-15）：`ironcalc_base`（计算）、`ironcalc`（读写 xlsx） | 0.8.0（2026-10-18），没发布到 crates.io |
| 怎么引用 | crates.io 版本号 | git 依赖，锁定一个提交：`gridcraft-engine` / `model` / `calc` / `xlsx` |
| 许可证 | MIT 或 Apache-2.0 | MIT 或 Apache-2.0（ArtCraft 名字和图标不在授权里） |
| 需要的 Rust | 稳定版 | ≥ 1.90，edition 2024 |
| 额外自带 | 上层 bindings（Python、Node、网页） | 命令注册表（313 个命令）、撤销历史、MCP 服务、命令行、数据透视表、图表 |

## 2. 比什么

### A. 正确性（硬门槛）

1. **公式对不对**：拿真实 Excel 存的 xlsx（里面带 Excel 算好的缓存值）当标准答案。用内核重算全部公式，和缓存值逐格比，数值容差 1e-9（相对）。样本用 Apache POI 的测试数据里所有 xlsx（几百个，覆盖面广）。输出：每个内核的通过率，以及出错最多的函数排行。
2. **读了再写不丢东西**：打开 → 存成 xlsx → 重新打开，所有格子的值、公式、数字格式要一致。
3. **中日文**：构造一批文件：中日文文字、中日文工作表名（公式里引用 `'数据'!A1`）、全角字符。只比对文字完全一致。
4. **不崩溃（硬门槛）**：把 POI 的 xlsx 在随机位置截断、随机改字节，各 200 次。统计 panic、卡死（> 10 秒）、内存暴涨（> 2 GB）。要求：零 panic、零卡死。办公软件打不开文件可以，但不能崩。

### B. 速度和内存（我们的核心卖点）

测试文件由我们自己生成（用 `rust_xlsxwriter` 的低内存模式），固定随机种子：

| 名字 | 内容 | 约多大 |
|---|---|---|
| S | 1 万行 × 20 列，数字、文字、日期混合 | 20 万格 |
| M | 10 万行 × 20 列 | 200 万格 |
| L | 100 万行 × 10 列（Excel 的行数上限） | 1000 万格 |
| F | 10 万行，每行 5 个公式（SUM、IF、精确 VLOOKUP、SUMIF） | 50 万公式 |
| Chain | 10 万个格子依次引用上一个（`B2=B1+1`…） | 深依赖，查栈溢出 |
| Fan | 100 万个公式都引用同一个格子 | 改一格全体重算 |
| Str | 100 万个互不相同的字符串 | 共享字符串表压力 |
| CJK | 10 万行中日文 | 多字节文字 |

每个内核 × 每个文件，量：

1. 打开时间（5 次取中位数，第一次冷启动单独记）
2. 打开后的内存：峰值、稳定后各记一个
3. 改一个格子后的重算时间。Fan 看整体重算；M 里的普通格子看**手感**：连续改 1000 次，记中位数和 p99，理想是 < 16 ms
4. 存成 xlsx 的时间和文件大小
5. 空工作簿的内存和初始化时间（对应「空表内存 < 50 MB」的指标）

### C. Agent 和人都好用（作者 2026-10-20 新增要求：AI 友好、人友好，集成 agent）

这一项看**内核提供的接口**，而不是界面：

| 检查项 | 看什么 |
|---|---|
| 命令层 | 所有编辑操作是不是都能用「名字 + 参数」调用？能不能列出全部命令和参数说明（给 agent 读）？ |
| 无窗口运行 | 不开窗口能不能打开、读取、修改、保存？（命令行、MCP） |
| 读出来的格式 | 能不能把一个区域读成文本表格（agent 好懂），而不只是二进制对象？ |
| 撤销 | agent 做的一批操作能不能合成一步撤销？人能不能看到 agent 改了什么？ |
| 原子批量 | 一批命令要么全成功，要么全不改？ |
| 错误信息 | 出错时是不是说得清楚、能照着改？例如 GridCraft 打不开 Excel 95 时说「BIFF5 不支持，请先另存为 .xlsx」，这种就是好的。要同时有给人看的话和给程序看的错误码 |
| 安全 | 能不能限制 agent 只能读、不能写？删除类操作能不能要求确认？ |
| 不依赖界面和系统接口 | 内核能不能编译成不带窗口库的版本？ |

GridCraft 的说明里有 MCP 服务、命令行和 JSON 控制通道；IronCalc 这块我没验证，实测时逐项确认，不预设结论。

### D. 构建和维护

- 发布版二进制大小（只含内核和测试入口，strip 后）
- 冷编译时间、依赖数量（`cargo tree`）
- 依赖的许可证（`cargo deny`），有没有 GPL 之类的
- 每个依赖有没有 `unsafe`；GridCraft 声明 `unsafe_code = forbid`，IronCalc 要查
- 近 3 个月的 API 变化量（用 git 历史看公开接口改了几次），代表升级成本
- 上游接不接受 AI 辅助写的贡献：看 CONTRIBUTING、行为准则和近期 PR 的处理。我们主要靠 agent 写代码，上游不收的话，修 bug 只能自己维护分支
- 能不能编译成 32 位（i686-pc-windows-gnu），见下面「32 位」

## 3. 怎么跑

**工作目录**：Carrysheet 仓库里的 `research/kernel-bench/`，一个 Cargo workspace（不加入将来产品的 workspace）：

```
gen/              生成测试文件
bench-ironcalc/   只依赖 IronCalc 的测试程序
bench-gridcraft/  只依赖 GridCraft 内核的测试程序
oracle/           用 Excel 缓存值做公式对比
fuzzlite/         截断、改字节
report/           把 JSON 汇总成表
run-all.ps1       在 Windows 上跑全部
```

每个内核一个独立程序，避免一个进程里两个内核互相影响内存。程序只输出 JSON 行，汇总交给 `report`。

**在哪里跑**：
- 开发和正确性测试在 WSL 里做（WSL 现在约 3 GB 内存、8 核，还有别的 agent 在用：编译限 `CARGO_BUILD_JOBS=2`，用 `nice`）。
- **速度和内存数字以 Windows 原生运行为准**：WSL 里交叉编译 `x86_64-pc-windows-gnu`，生成的 .exe 从 WSL 直接启动（上次测 GridCraft 就是这样），内存用程序自己调用 `GetProcessMemoryInfo` 读 PeakWorkingSetSize。L、Fan、Str 这类大文件只在 Windows 上跑（WSL 的 4 GB 放不下）。
- 最终数字发布前再用 msvc 版本复测一次。

**32 位**（作者 2026-10-20 要求也做 x86）：两个内核都编 `i686-pc-windows-gnu` 版，跑空工作簿、S、M、F。32 位进程最多用 2 GB 地址空间（加 large-address-aware 标志、在 64 位 Windows 上是 4 GB），记下每个内核在 32 位下最大能打开多大的文件。编不过 32 位的内核，这一项记为不通过。

**资源限制**（后台任务最多占一半）：
- 固定 `RAYON_NUM_THREADS=4`，两个内核同样条件。
- 进程设成低于正常优先级。
- 任何一次运行工作集超过 6 GB 就自动杀掉，记为「内存不足」。

**工具**：Rust 稳定版、`x86_64-pc-windows-gnu` 和 `i686-pc-windows-gnu` 两个目标、`mingw-w64` 交叉编译器（2026-10-20 已装）。

## 4. 怎么选（建议的规则）

1. **硬门槛**：A4 零崩溃。不过的先淘汰；两个都不过，先停下来想办法，不选。
2. **公式通过率**：差距 > 5 个百分点，选高的；否则看下一条。
3. **内存和速度**：GridCraft 内存 ≤ IronCalc 的 1.5 倍，选 GridCraft（功能多得多，还有现成的命令层和 MCP）；超过 2 倍，选 IronCalc；1.5–2 倍之间，看 C 项和 D 项。
4. 大文件的绝对数字（10 万、100 万行打开多久、占多少内存）借这次结果定下来，写回指标。

## 5. 预计做多久

- 公式对比和截断测试：1 天
